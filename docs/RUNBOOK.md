## اجرا

- [توسعه]: `npm.cmd run dev`، سرور و فرانت را با هم باز کند. فروشگاه `http://127.0.0.1:8443/`؛ مدیر `http://localhost:8443/`؛ سرور `http://127.0.0.1:3001`. پایگاه در `server/data/store.sqlite` ساخته شود.
- [اجرای جدا]: اگر فرانت از قبل باز است، فقط `node server/index.mjs` اجرا کن. برای فرانت تنها، `npm.cmd run dev:frontend`. درخواست `/api` به سرور در ۳۰۰۱ رود. پردازه تکراری نساز.
- [ساخت]: `npm.cmd run build` سپس `npm.cmd start`. فروشگاه `http://127.0.0.1:3001/` و مدیر `http://localhost:3001/`. خود سرور فایل‌های `dist` را هم دهد. DNS یا تغییر فایل hosts لازم نیست.
- [مرز مدیر]: `localhost` برای مدیر؛ `127.0.0.1` برای فروشگاه. نقش مدیر در پایگاه و میزبان درخواست هر دو بررسی شوند. حساب مدیر روی فروشگاه وارد نشود؛ مشتری روی میزبان مدیر وارد یا ثبت نشود. `/admin` و `/api/admin/**` روی فروشگاه همیشه ۴۰۴ دهند.
- [مدیر]: `node server/admin.mjs --email admin@example.test --name "مدیر فروشگاه"`. ایمیل نمونه را عوض کن. رمز در ترمینال پنهان گرفته شود. رمز آماده وجود ندارد.
- [بازیابی مدیر]: همان فرمان با `--reset`. فقط اپراتور میزبان اجرا کند. حساب هم‌نام مدیر شود و نشست‌های پیشین آن باطل شوند.
- [فایل رمز]: اجرای بی‌تعاملی، `ADMIN_PASSWORD_FILE` به فایل خصوصی بیرون مخزن اشاره کند؛ نمونه مسیر با `Join-Path $env:USERPROFILE 'Documents\Private\autokala-admin-password.txt'`. فقط حساب کاربر خود دسترسی داشته باشد. فایل فقط رمز ۱۲ تا ۱۲۸ کاراکتر داشته باشد. رمز در آرگومان، گفتگو یا سند نده. پس از ساخت، فایل موقت رمز پاک و متغیر محیط از همان پوسته برداشته شود.
- [آزمون]: `npm.cmd test`، ابتدا سرور و سپس فرانت. جدا: `npm.cmd run test:backend` و `npm.cmd run test:frontend`. تست سرور به‌ترتیب و فرانت با یک thread اجرا شود. پایگاه و پوشه موقت، جدا از فروشگاه. تست، داده محلی فروشگاه را عوض نکند.
- [نوع]: `npm.cmd run typecheck`. ساخت و بررسی نوع هر دو لازم.
- [محیط]: فایل محیط خودکار خوانده نشود. مقدارها را در محیط پردازه بده؛ یا `node --env-file=.env.local server/index.mjs` با فایل خصوصی محلی.

| متغیر | پیش‌فرض | کار |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | نشانی گوش‌دادن؛ برای میزبان عمومی با بررسی شبکه عوض شود |
| `PORT` | `3001` | پورت سرور؛ فرانت پورت جدا دارد |
| `PUBLIC_HOST` | `127.0.0.1` در توسعه | میزبان دقیق فروشگاه، بدون پروتکل؛ پورت اختیاری |
| `ADMIN_HOST` | `localhost` در توسعه | میزبان دقیق و جدا برای مدیر، بدون پروتکل؛ پورت اختیاری |
| `DB_PATH` | `server/data/store.sqlite` | مسیر داده؛ برای فرمان مدیر و پشتیبان هم همان باشد |
| `NODE_ENV` | خالی | روی میزبان نهایی `production` |
| `ALLOWED_ORIGINS` | خالی | مبدأ کامل مجاز، جدا با ویرگول؛ مانند `https://shop.example.test` |
| `SECURE_COOKIES` | `false` | زیر HTTPS مقدار `true` |
| `TRUST_PROXY` | `false` | فقط پشت یک پراکسی مورد اعتماد روی loopback، `true` |
| `ADMIN_PASSWORD_FILE` | خالی | فقط فرمان مدیر؛ فایل خصوصی رمز |

- [سلامت]: `/health/live` زنده‌بودن پردازه. `/health/ready` خواندن پایگاه و `staticBuilt` وجود ساخت را دهد. این پاسخ، درگاه و فروش واقعی را اثبات نکند.
- [محلی]: `NODE_ENV=development`، `HOST=127.0.0.1` و `SECURE_COOKIES=false` بمانند. `PUBLIC_HOST=127.0.0.1` و `ADMIN_HOST=localhost` بدون پورت، هر دو اجرای ۳۰۰۱ و ۸۴۴۳ را پوشش دهند. میزبان ناشناس ۴۲۱ دهد؛ `X-Forwarded-Host` راه عبور نیست.
- [نشست]: مشتری `autokala_session`، عمر ۱۴ روز و `SameSite=Lax`. مدیر `autokala_admin_session`، عمر ۸ ساعت و `SameSite=Strict`. هر دو `HttpOnly` و فقط میزبان خود؛ `Domain` ندارند. خروج، نشست را باطل کند.
- [انتشار آینده]: برای `NODE_ENV=production`، دو نام DNS جدا و صریح، HTTPS و `SECURE_COOKIES=true` لازم؛ نبودشان شروع را ببندد. کوکی HTTPS پیشوند `__Host-` گیرد. دو پورت روی یک نام میزبان، جداسازی کوکی نیست. این تنظیم، اکنون اجرا نشود؛ دامنه عمومی تعیین نشده.
- [پراکسی]: `HOST=127.0.0.1` بماند. با `TRUST_PROXY=true` فقط اتصال loopback برای IP کاربر پذیرفته شود. پراکسی IP واقعی را آخر `X-Forwarded-For` بگذارد؛ `X-Forwarded-Proto` را بازنویسی کند. چند پراکسی زنجیره‌ای، بررسی جدا خواهد.

- [پشتیبان زنده]: `node server/backup.mjs backups/store-2026-10-21.sqlite`. نام تازه بده. فرمان، `VACUUM INTO` و بررسی یکپارچگی اجرا کند. مقصد موجود را بازنویسی نکند.
- [کپی سرد]: سرور را تمیز ببند. از کل پوشه داده در جای امن، کپی زمان‌دار بگیر. هنگام اجرای سرور، تنها فایل اصلی را کپی نکن؛ فایل WAL شاید داده تازه دارد.
- [بازگردانی]: سرور را ببند. از پوشه داده فعلی یک کپی جدا بگیر. فایل‌های فعلی پایگاه و `-wal` و `-shm` را از مسیر فعال کنار بگذار. فایل پشتیبان سالم را به `DB_PATH` برگردان. فایل قدیمی WAL کنار پایگاه برگشتی نماند. سرور را باز کن. سلامت، ورود مدیر و سفارش پیشین را بخوان.
- [حفظ]: پشتیبان، نشانی و شماره مشتری دارد. دسترسی محدود و دیسک رمزدار خواهد. دوره نگهداری و پاک‌سازی با مالک تعیین شود.
- [آزمون]: بازگردانی روی کپی جدا اجرا کن. پایگاه اصلی محل تست نیست.
